## 3. 高优先级边界与复现任务

### P0-A：会话对象归属

证据：[main.py](/Users/zhitong/Desktop/AI-Agent/ai-job-agent/app/main.py) 的聊天请求取客户端 `session_id`；
[PostgresSessionStore](/Users/zhitong/Desktop/AI-Agent/ai-job-agent/app/postgres_session_store.py) 只按 `session_id` 查写；
[RedisSessionCache](/Users/zhitong/Desktop/AI-Agent/ai-job-agent/app/redis_session_cache.py) 同样按会话 key 缓存。
当前代码路径没有会话所属 user/tenant 校验，不能说「JWT 已保证所有聊天数据隔离」。

复现：仅用本地测试账号 A/B，让 B 请求 A 的 session_id；断言不能读取 A 历史，也不能追加。
修复方案：会话表记录 tenant/user；服务端创建 ID；查写先验证归属；SQL、缓存 key、限流 key 同步纳入身份范围。
缓存加前缀不能代替数据库归属验证。验收跨用户、跨租户、伪造 ID 和并发写。

### P0-B：审批与 trace 归属

证据：[ApprovalStore](/Users/zhitong/Desktop/AI-Agent/ai-job-agent/app/approval.py) 是进程内 `dict + queue.Queue`；
`/agent/approve` 只校验登录，未校验审批与 user/run/tool 的归属；`/agent/traces/{trace_id}` 未声明身份依赖。
审批按 request_id 等待，不逐个绑定 tool_call，且可以提前 `decide` 入队。

复现：B 提交 A 的审批 ID、读取 A trace、在请求尚未到达审批节点前预先决定；都应拒绝。
改进：持久化 approval_id、user/tenant、run_id、tool_call_id、参数 hash、过期时间、状态；原子一次性消费。
审批只允许 `pending → approved/rejected/expired`，参数变更使授权失效。多实例不要依赖进程内队列。

### P0-C：Graph 的 tenant 参数不是 checkpoint 隔离

证据：[supervisor_graph.py](/Users/zhitong/Desktop/AI-Agent/ai-job-agent/app/supervisor_graph.py) 的 `_run_config` 只有 `thread_id=run_id`。
读、恢复图时 `tenant_id` 用于状态字段/部分 memory namespace，而非 checkpoint key 的归属验证。
HTTP start 没有传 `memory_store`；幂等 lookup 需要 `request_id and memory_store`，所以默认 HTTP 路径没有这层去重。
即使传入 memory_store，现有「先查再写」也不是并发原子 claim。

复现：A 创建 run，B 用该 run_id 查询、恢复；同 request_id 并发 start；对比副作用调用次数。
改进：run 表绑定归属，读/恢复前授权；checkpoint key 使用服务端 namespace；请求唯一约束/原子占位。
不要只修改返回的 tenant_id 字段。图存储隔离和对象级授权需要一起做。

### P1-A：超时返回不等于执行取消

证据：`_invoke_with_timeout` 使用 `future.result(timeout)`，随后 `shutdown(wait=False, cancel_futures=True)`。
已经开始的线程不会被这个参数强制终止，可能在 API 返回 failed 后继续写 checkpoint 或调用工具。
`/graph/start` 默认没有 timeout，且同步执行会占用 async 路由的事件循环。

练习：slow fake tool 在超时后写标记，观察是否仍写入；设计独立进程/容器强制终止，或在每步落实协作取消。
面试说「限制等待时间的演示实现」，不能说「已取消全部后台执行」。

### P1-B：流式限流、重试与计费边界

证据：[async_llm.py](/Users/zhitong/Desktop/AI-Agent/ai-job-agent/app/async_llm.py) 的 semaphore 只包 `create`，流创建后即释放；
成本记账只在 `not stream`。重试覆盖建流时错误，不覆盖后续 async iteration。
[main.py](/Users/zhitong/Desktop/AI-Agent/ai-job-agent/app/main.py) 的 token 配额是预估消耗，不是真实 usage 结算。

练习：两个慢 stream，检查活跃流数量；断流后确认错误终止事件和清理。改进时 semaphore 覆盖读取/关闭，
部分输出后避免透明重试重复 token；记录实际 usage，必要时标记 estimated 并做预扣/结算。

### P1-C：RAG 图不等于默认请求链路

证据：[async_agent.py](/Users/zhitong/Desktop/AI-Agent/ai-job-agent/app/async_agent.py) 直接 `retriever.retrieve`，没有查询改写调用。
`build_retriever` 返回 `HybridRerankRetriever`；旧 `PersistentHybridRetriever` 是不同版本。
当前 builder 未显式完成它自己的 chunk 编码/upsert，而 HybridRerank 初始化只建 BM25。
是否已入库依赖外部初始化路径，不能只凭本 builder 宣称冷启动自动入库完成。

另外 `HybridRerankRetriever.retrieve(filters=...)` 只过滤 vector 分支；BM25 全局取候选后并集，
不能据此宣称端到端 metadata 权限过滤。实际聊天并未传租户 filter。
验证时用空 collection 和两个租户的 fixture，覆盖入库、过滤、并集和后处理。

现有 `tests/test_hybrid_rerank_retriever.py` 的 filter 用例只断言参数传给 store，
没有断言最终 BM25 并集排除了其他租户；此类测试通过也不能证明端到端 ACL 正确。

### P1-D：评测与压测口径

`rag_eval_cli` 未传 answer_fn；`evaluate_rag_end_to_end` 使用 reference_answer 作为 answer。
检索分数可以来自实际检索，但此模式的生成指标不能代表模型真实生成质量。
`citation_coverage` 验证引用 ID 是否在召回里，不验证论断是否被证据支持。
`BenchmarkRunner.build_report` 用 `success / avg_ms` 估 throughput，未使用压测总墙钟时长；并发下不能当真实 RPS。
worker 的计时还包含 semaphore 排队。修复与实验见 11/12。
