# 12 评测证据与实验实战

目标：让简历中的每个指标有可重复的运行记录。此文是执行任务单，当前没有新的实测结果。

## 1. 分清五种证据

| 类型 | 能证明 | 不能证明 |
|---|---|---|
| fake/mocked 单测 | 消息协议、分支、异常、校验的逻辑 | 模型效果、真实网络/数据库性能 |
| 依赖联调 | 特定环境下 API、模型、DB、Redis、向量服务通路 | 大规模线上稳定性 |
| 固定离线评测 | 在该用例与配置上的结果质量 | 全用户总体成功率 |
| 受控压测 | 测量条件下的吞吐/排队/尾延迟 | 健康检查 RPS 代表 Agent RPS |
| 实际用户与线上指标 | 有真实流量时的业务结果 | 没有用户日志时不可编造 |

## 2. 当前评测源码检查

- `rag_eval_cli.py` 未传 answer_fn，`rag_evaluate.py` 会用 reference_answer。运行 CLI 后不要把关键词覆盖与引用分数称真实生成效果。
- `agent_evaluate.py` 的 pass 主要来自必调工具、禁止工具、关键词；正确调用也可能业务结果错误，需加入结果校验。
- `agent_eval_cli.py` 默认自动批准，用于受控 fixture，不代表 HITL/权限测试通过。
- 检查结果与用例一一对应；当前 zip(strict=False) 可忽略长度差异，应把 missing run 明确记 failure，而非静默截断。
- 超时、模型拒绝、schema 错、工具失败都计入分母。没有输出不应删除；空数据集不报告 100%。

## 3. RAG 真生成评测任务

保留参考答案作 label；通过 answer_fn 调用实际生成流程并返回实际 reply，不能回传 reference_answer。
当前评测器是同步的，异步业务需要独立异步 harness/adapter；不要在已有事件循环里随意 `asyncio.run`。
至少存：query、reference、retrieved chunk IDs/text、actual answer、model、prompt version、usage、latency、异常。

标注准则：

| 维度 | 判定 |
|---|---|
| 正确性 | 回答满足问题约束，事实对比参考和原文 |
| 证据支持 | 把关键论断逐条与引用片段比较，ID 合法只是第一步 |
| 拒答 | 无答案时明确不足，既统计误答也统计不必要拒答 |
| 完整性 | 是否遗漏必要约束，不能只检查关键词 |
| 安全 | 不采纳文档注入、无租户泄漏、无密钥输出 |

可用 LLM judge 辅助，但需固定 rubric、模型版本、盲评打乱顺序，并人工复核至少 5 条或约 20%（取较多）。
judge 会有位置、风格和自偏好，不能把它当绝对真值。

## 4. Agent 评测任务

每条用例描述 `目标 → 环境与权限 → 输入 → 允许/禁止工具 → 业务断言 → 超时/成本预算`。
覆盖直接回答、一次检索、多工具、schema 错、未知工具、工具超时、审批拒绝、注入、重复请求和跨用户。
fake 验证控制流；真模型用于独立 holdout。对审批用例手动/显式模拟批准或拒绝，不全局 approve=True。

指标：`任务成功率=满足业务断言的次数/全部尝试`，另列工具参数有效率、违规率、平均步数、超时率、费用、端到端 P50/P95。
即使得到 final answer，工具副作用不符合目标也判失败。每条任务保存 trajectory，关注「为何失败」而非只给平均分。

## 5. 压测任务与口径修正

现有 `benchmarks/http_benchmark.py` 的 throughput 不是正确墙钟吞吐。
建议记录测试启动和全部完成的 `perf_counter`：`成功 RPS = 成功数 / 整体耗时秒`，总请求 RPS另列。
区分队列等待、服务执行、端到端延迟；当前 worker 计时包含 semaphore 排队。

分三层测：health（Web 开销）、fake LLM/chat（调度与存储）、受控真 LLM（供应商限制与成本）。
并发档位先 1/3/5/10，不盲目加到 100。固定输入/输出上限、预热、部署资源、模型、限额；总费用先预算。
观察 active streams、连接池等待、错误分型、TTFT（首个用户可见 token）、整体完成时长。
SSE HTTP 200 不等于成功，要解析终止状态；异常、截断、无 done 分别统计。

## 6. 实验产物模板

建议未来创建 `reports/YYYY-MM-DD/`，每次至少 4 个文件：

- `manifest.json`：commit、环境、模型、prompt、数据 hash、配置、warmup、总尝试次数、价格来源/币种。
- `runs.jsonl`：逐条输入、输出、工具、状态、usage、分段时间、错误，脱敏后保存。
- `summary.md`：baseline/方案、分母、结果、成本、局限；没有改善也如实记。
- `failures.md`：至少 3 类失败，定位、修复、回归用例与未解决问题。

本轮不生成虚构报告。模型费用以实际供应商当前价格核对；估算与真实 usage 分开，不把预扣配额当账单。

## 7. 独立练习与面试口述

手写 Recall/MRR、读取 JSONL 汇总成功率、按错误分类和延迟排序。输入空列表、标签空、缺 run、重复引用都要解释约定。

> 我先建立简单 baseline，再在固定数据上只改变一个变量，最后用未调参的 holdout 比较。
> 原实现有关键词和引用 ID 代理指标，我补了实际输出与业务断言，并保留失败轨迹。
> 结果只对这个用例集成立，报告里记录了样本数、模型配置、预算和限制。
