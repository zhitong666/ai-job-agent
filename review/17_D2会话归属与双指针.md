**1.2 逐题批改与正确答案（原答保持不变）。**

1. `sub` 是 JWT 的**用户主体标识**，`tenant_id` 是**租户标识**；它们是 `TokenPayload` 的两个并列字段，不是 `sub` 从 `tenant_id` 推导出来。你识别到 B 可能拿到 A 的历史，但不需要“遍历 PostgreSQL”或枚举所有会话；只要 B 知道、猜到或从别处得到 A 的 `session_id`，合法 JWT 只证明 B 的身份，不能证明这个会话属于 B。源码见 [认证模型](../app/auth_models.py)、[路由](../app/main.py)。
2. 你画出的缓存未命中链大体对，但“丢失 user”的**决定点**是路由调用 `stream_answer_question_async` 只传 `session_id` 而不传 `user.sub/tenant_id`；之后 `_load_history`、`RedisSessionCache.get_messages`、`PostgresSessionStore.get_messages` 均只有 `session_id`。检索、`format_context`、messages 裁剪不是对象授权点。限流 key 也只含 `session_id`，会造成跨用户计数干扰；额度调用仍使用 `user.sub/roles`，所以不能说所有地方都丢了 user。若 `session_store is None`，代码转用进程内 `in_memory_session_store`，不是初始化 PostgreSQL store。
3. **不能解决。** 即使 Redis key 变成 `tenant:user:session`，B 的缓存未命中后仍会执行 `WHERE session_id = %s`，把 A 的消息从 PostgreSQL 读出并写入 B 的新缓存 key。隔离缓存命名空间是必要的辅助，数据库查询与写入仍必须校验 owner，而且不能让缓存命中绕过归属校验。
4. 让客户端任意指定 ID 并“首次访问即绑定”，可能出现 A/B 并发抢占同一 ID、旧会话无 owner 无法可信认领、重试时创建重复或错误绑定。较清楚的设计是服务端生成不可预测 ID，在独立的会话元数据中原子记录 `(session_id, tenant_id, owner_sub)`，后续请求只允许该 owner 使用；旧数据先区分可证明归属与无法证明归属，不能把旧 ID 自动授予第一个来访者。具体迁移策略留在 2.2 由你选择。
5. **四条路径都不能只信客户端 ID。** 读缓存前检查会话归属；缓存未命中后的 PostgreSQL 查询仍带 owner；写入在数据库层再次保证 owner 并保持 user/assistant 两条同事务；限流 key 至少含服务端身份，避免 B 用 A 的 ID 消耗 A 的窗口。对“存在但非本人”的会话选统一的 403 或统一的 404 均可，404 更少泄露对象存在性；HTTP 流开始前完成拒绝，不能先返回 200 再在 SSE 内补“403”。

> 我的复杂度与边界解释：（这格原先留空，下方为助手补充，不冒充你的闭卷回答。）

**助手补充的面试解释。** `i=m-1` 指向 `nums1` 有效区末尾，`j=n-1` 指向 `nums2` 末尾，`k=m+n-1` 指向 `nums1` 尚未写入的末尾。每轮把两个候选中较大的数写到 `k`，随后移动对应读指针和 `k`；这样写入区从右往左保持有序，也不会覆盖尚未读取的 `nums1` 有效元素。循环条件只需 `j>=0`：`nums2` 写完后，`nums1` 剩余元素本来就在正确位置。

**复杂度。** 每轮 `i` 或 `j` 至少减少 1，最多写 `m+n` 次；时间 O(m+n)。除三个下标外只原地改 `nums1`，额外空间 O(1)。**边界。** `n=0` 时循环不执行；`m=0` 时全部复制 `nums2`；`nums1[i]` 更小、相等或有负数时仍从大到小写入。相等时你的 `>` 判断先写 `nums2[j]`，`nums1` 中相等元素会留在其前面，不影响排序。前提是两数组各自已经升序，且 `nums1` 长度为 `m+n`；不需要把末尾占位的零当作有效数据。
