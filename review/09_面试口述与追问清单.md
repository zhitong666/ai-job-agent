## 1. 两个版本的项目自述

### 30 秒电梯版

```text
我做的是一个 AI 求职分析 Agent。

它解析 JD，从知识库检索相关主题，生成技能差距和学习建议。
技术上用 FastAPI 提供 API，DeepSeek 做 LLM，
ReAct 让 Agent 自主调用知识库工具，RAG 提供检索能力，
后面又补了 Supervisor、LangGraph、MCP、安全和生产化，
最后用 Docker 和 GitHub Actions 完成部署。

我最有收获的是把 Agent 从固定流程演进到可恢复、可审计的有状态多 Agent。
```

### 5 到 8 分钟详细版

建议按七段讲：

```text
1. 定位：解决 JD 解析、知识库检索、岗位分析和学习建议。
2. 技术栈：FastAPI + React + DeepSeek + RAG + LangGraph + MCP + Docker。
3. 架构：前端 -> Nginx -> FastAPI -> Agent 编排层 -> 工具/ RAG -> 外部服务和数据层。
4. Agent 主线：ReAct 循环、ToolRegistry、审批、状态、Plan、Supervisor、LangGraph。
5. RAG 主线：切分、Embedding、混合检索、重排、查询改写、评估。
6. 生产化：异步、PostgreSQL、Redis、队列、JWT、安全、可观测、CI/CD。
7. 最有价值的取舍：例如低内存部署用远程 Embedding，或 LangGraph checkpoint 如何做幂等。
```

## 2. 口述必背的四个闭环

```text
RAG：
切分 -> Embedding/入库 -> 混合检索 -> 重排 -> 注入生成 -> 引用来源
查询改写是独立可选能力，默认聊天没有接入；冷启动入库需另行验证。

```

## 3. 高频问题与回答线索

### Agent 基础

**什么是 AI Agent？**

```text
LLM 是推理核心，但不是一次问答。
Agent 在循环中理解目标、拆解任务、选择工具、调用工具、观察结果、更新上下文，最后交付。
与聊天机器人相比，它有状态、能操作外部系统、能多步执行。
```

**ReAct 的 Reason、Act、Observe 分别由谁完成？**

```text
Reason 由 LLM。
Act 的“建议”由 LLM，真正执行由 Python ToolRegistry。
Observe 是工具返回值，通过 role=tool 回填。
```

**怎么防死循环？**

```text
max_steps、finish 工具、异常转 observation，多 Agent 再加 MAX_HANDOFFS。
```

### Function Calling

**模型返回 tool_calls 后发生了什么？**

```text
解析 name 和 arguments -> registry 查工具 -> 参数护栏 -> 审批判断 -> 执行 handler -> 回填 assistant tool_calls + tool result。
```

**怎么保证结构化输出稳定？**

```text
Pydantic 生成 JSON Schema；统一 parse_and_validate；清理代码围栏；
解析失败时保留原 tool_calls 并追加 tool 错误消息，让模型重试。
```

### RAG

**RAG 完整链路？**

```text
切分、Embedding、入库、向量 + BM25 混合、重排、上下文注入、生成和来源。
查询改写是扩展能力，不在当前默认聊天路径。
```

**为什么混合检索？**

```text
向量擅长语义，BM25 擅长精确词法；归一化后加权互补。
```

**怎么评估？**

```text
Recall@K、Precision@K、MRR、NDCG，以及 citation coverage 和关键词覆盖。
后两者只是代理指标；现有 RAG CLI 默认用参考答案，评真实生成必须接实际 answer_fn。
```

### 多 Agent

**ReAct 和 Plan-and-Execute 区别？**

```text
ReAct 逐步动态决策；Plan 先规划再按依赖执行。
ReAct 灵活，Plan 轨迹清晰、可审计、可恢复。
```

**Supervisor 职责？**

```text
只路由，不直接回答；输出结构化 SupervisorDecision。
```

**LangGraph 的价值？**

```text
显式状态图、checkpoint、中断恢复、状态查询，可加超时、幂等、租户隔离。
```

### MCP 与安全

**MCP 和 Function Calling 关系？**

```text
Function Calling 是模型表达工具调用；MCP 是工具系统侧的标准连接协议。
MCP Client 把 Server schema 转成 OpenAI Function Schema。
```

**如何防御提示注入？**

```text
输入关键词和模式检测、工具参数递归清洗、外部数据视为不可信内容、日志和 Trace 脱敏、红队验证。
```

### 生产化

**为什么异步化？**

```text
LLM 和数据库主要是 I/O；异步并发等待外部请求，信号量限制并发，提高吞吐并保护上游。
```

**Redis 承担哪些职责？**

```text
会话缓存、限流、任务状态、arq 队列。
```

**长任务为什么用队列？**

```text
API 快速返回 202，长任务不占请求线程，Worker 可独立扩展，状态可查询。
```

**怎么做多租户隔离？**

```text
设计应从可信 identity 出发，把归属校验落实到每条查询、恢复、审批和缓存 key。
当前部分任务查询和共享记忆有 tenant 范围，但聊天、审批与 checkpoint 仍有缺口；
不能把 JWT 或 memory namespace 说成整个系统已隔离。
```

**日志、指标、Trace 区别？**

```text
日志回答单次请求发生了什么；指标回答整体趋势；Trace 回答一次请求跨服务路径。
```

**重试、熔断、降级、背压区别？**

```text
重试解决瞬时错误；熔断在持续失败时快速拒绝；
降级提供兜底结果；背压限制并发防止过载。
```

## 5. 故障追问模板

### 问题：线上 Agent 卡住不返回，怎么排查？

```text
1. 看 request_id 关联的日志和 Trace，确认卡在输入护栏、LLM 还是审批。
2. 如果卡在审批，检查 /agent/approve 是否到达，以及 ApprovalStore 是否超时。
3. 如果卡在 LLM，看重试次数、超时、信号量和上游是否限流。
4. 如果卡在图执行，查 LangGraph checkpoint 的 next_nodes 和 interrupts。
5. 最后看 Redis/PostgreSQL 健康检查和连接池是否耗尽。
```

### 问题：缓存里一直是旧会话，怎么办？

```text
先确认写入顺序：PostgreSQL 成功后才删除 Redis key。
如果写库成功但删除缓存失败，会出现旧缓存，需要失败重试或事务性缓存失效。
当前实现是简单 Cache Aside，面试时可以说明可演进方向。
```

### 问题：向量维度不匹配怎么办？

```text
确保 Embedding 模型、collection 创建维度和查询向量一致。
项目 collection name 包含 dimension 和模型 hash，换模型会自动切到新 collection。
```
