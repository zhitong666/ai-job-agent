#### 2.3.1 生产方案补充：有没有更优雅的建会话方式？

**先分清两个问题：谁生成 ID，以及何时创建归属行。** 无论 ID 来自前端还是后端，真正需要持久化的会话只能在“首条消息之前单独创建”或“首条消息处理时创建”。因此没有绕开这两个时机的第三种魔法接口；更好的体验来自清晰的请求契约、幂等重试和统一的归属服务。

- **方案 A：单独创建。** `POST /chat/sessions` 返回服务端 ID；之后 `/chat`、`/chat/stream` 都只接收已归属的 ID。建会话与发消息边界清楚，适合会话列表、跨设备续聊，也便于本轮逐层测试。代价是首条消息前多一次请求，创建成功而发消息失败会留下空会话，可定期清理。
- **方案 B：首条消息懒创建，这是 2.1 原方案的生产级完善。** 请求把 `session_id` 设为 `null`，同时带一次用户操作唯一的 `client_request_id`；服务端先认证、限流/额度检查，再原子创建并提交 `(session_id, tenant_id, owner_sub)`，最后才开始 LLM 流。`/chat/stream` 在返回 `StreamingResponse` 前确定 ID，可通过 `X-Session-ID` 响应头交给当前使用 `fetch` 的前端；若改用 SSE `session` 事件，也必须先于内容事件发送并处理断流。非流式 `/chat` 在 JSON 中返回 ID。已有 ID 的请求走相同的归属校验；两个路由复用同一个 `get_or_create_session` 服务，不各写一套规则。若前后端跨域且使用自定义响应头，还需在 CORS 中暴露该头。此方案没有额外建会话请求，但响应头丢失、客户端重试和流中断时更难做对。
- **方案 C：前端预生成随机 ID，再显式注册归属。** 例如前端为离线草稿/多标签页预留 UUID，调用幂等的 `PUT /chat/sessions/{id}` 让服务端确认 owner，再发消息。它改变的是 **ID 生成者**，创建时机仍属于方案 A；不能把“第一次携带此 ID 的请求”当作旧会话的认领凭据。当前前端已本地生成 ID，但后端尚未建立归属，因此**现状不是可直接上线的方案 C**。

**方案 B 必须补齐的生产约束。** 给创建请求键加 `(tenant_id, owner_sub, client_request_id)` 唯一约束；同一键重试返回同一 `session_id`，同键却换问题内容应报冲突。还要给“这一轮消息/LLM 执行”单独做幂等状态，否则虽然没创建第二个会话，断流重试仍可能重复调用模型、扣费或保存两轮消息。会话行应在开流前提交，不能在等待 LLM 的整个过程中持有数据库事务；客户端没收到头或首事件时复用同一 `client_request_id` 重试。所有已有会话读取、写入和缓存命中仍必须依据 JWT 中的 `tenant_id/sub` 查归属；随机 ID 只是定位符，不是授权凭证。旧无 owner 数据依旧不能自动认领。HTTP `POST` 本身不会让这些重试自动变成幂等。[HTTP 语义标准](https://www.rfc-editor.org/rfc/rfc9110.html)、[OWASP 对象级授权要求](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/)。

**本轮取舍。** D3 继续以方案 A 作为 2.3 的实施与验收契约：先修复可复现的跨用户读写，再考虑减少首条消息的一次请求。若以后更看重“点发送即开聊”，方案 B 是合理升级，但需连同响应 ID、创建幂等和消息轮次幂等一起改；不要只把 `session_id` 改成可空。无论选 A/B/C，A 的会话被 B 持有、旧 ID、Redis 命中和流开始前拒绝的验收标准都相同。

#### 2.3.2 详细操作版：按什么顺序改、每步看什么结果

##### **第 1 步：核对归属表，不改旧迁移（约 15 分钟）。** 

先读 [001_initial.sql](../migrations/001_initial.sql)：`chat_messages` 当前只有 `session_id`，没有 owner。再核对工作区已有的 [003_chat_sessions.sql](../migrations/003_chat_sessions.sql) 草稿是否含 `session_id TEXT PRIMARY KEY`、`tenant_id TEXT NOT NULL`、`owner_sub TEXT NOT NULL`、`created_at TIMESTAMPTZ NOT NULL DEFAULT now()`；主键保证同一 ID 只能有一条归属行。阅读 [db_cli.py](../app/db_cli.py) 中 `run_migrations()` 按文件名排序和 `schema_migrations` 记版本的逻辑。若 `003` 未应用，可在**测试库**运行 `.venv/bin/python -m app.db_cli migrate`；若已应用而需变更，新增下一版迁移，不能指望改旧文件生效。**不要**自动用已有 `chat_messages` 的 ID 给旧数据认领 owner。**验收**：测试库有 `chat_sessions`，旧消息仍在但无归属的旧 ID 不能通过后续授权；没有测试库时记录“SQL 已审阅，未实跑迁移”。

##### **第 2 步：让 PostgreSQL store 成为归属事实来源（约 25 分钟）。**

 修改 [postgres_session_store.py](../app/postgres_session_store.py)：

1. `create_session(tenant_id, owner_sub) -> str`：服务端用 `uuid.uuid4()` 等随机 ID；`INSERT INTO chat_sessions(session_id, tenant_id, owner_sub)` 成功并提交后才返回 ID。不要 `ON CONFLICT DO UPDATE owner_sub`；极罕见的 ID 冲突只能换新 ID 重试或报错，不能覆盖原 owner。
2. `authorize_session(session_id, tenant_id, owner_sub)`：`SELECT 1 FROM chat_sessions WHERE session_id=%s AND tenant_id=%s AND owner_sub=%s`。查不到时统一抛一个可被路由映射为 404 的领域异常；“ID 不存在”和“别人的 ID”不能靠响应区分。
3. 把 `get_messages` 签名改成接收 `session_id, tenant_id, owner_sub`，SQL 用 `chat_messages m JOIN chat_sessions s ON s.session_id=m.session_id`，并在 `WHERE` 同时限制三个字段，保留 `ORDER BY m.id ASC`。合法新会话没有消息时返回 `[]`，不要把空历史误判为未授权。
4. 把 `append_turn` 签名同样扩成三个身份字段加 `question, answer`。在**一个事务**里先按三元组查归属（若会话可能并发删除，用 `FOR UPDATE` 锁行），确认存在后插入 user 与 assistant 两条；任一插入失败则 rollback。调用者不得在等待 LLM 期间持有此事务。

**验收**：A 可读写、B/C 不能读写；冲突 ID 不改 owner；第二条插入失败后该轮两条消息都不存在。现有 `test_postgres_backend.py` 的 `AsyncMock` 游标需要新增 `fetchone` 返回与新的 SQL/参数断言，不能只改生产函数签名。

##### **第 3 步：Redis 命中也要受授权约束（约 15 分钟）。** 

改 [redis_session_cache.py](../app/redis_session_cache.py)：`create_session/authorize_session` 可直接代理到底层 PostgreSQL；`get_messages/append_turn/_key` 显式接收 `tenant_id, owner_sub, session_id`，例如 key `chat:session:{tenant_id}:{owner_sub}:{session_id}:messages`。`get_messages` **先**调用 PostgreSQL `authorize_session`，再读 Redis；未命中时用带身份的 `get_messages` 回源。`append_turn` 先让 PostgreSQL 事务写成功，再删除同一 key；写失败不得误删缓存。**验收**：[缓存测试](../tests/test_redis_backend.py) 中 A 命中时可跳过 PostgreSQL **消息查询**，却仍必须经过 PostgreSQL **归属检查**；A 未命中可回源；B 命中/未命中均不能读 A 历史或新建自己的假缓存。旧测试名“命中 Redis 无需 PostgreSQL”也要改成准确含义。

##### **第 4 步：路由在流开始前拒绝（约 20 分钟）。** 

在 [main.py](../app/main.py) 的聊天路由附近新增 `POST /chat/sessions`，以 `status_code=201` 返回 `{"session_id": "..."}`；只从 `Depends(get_current_user)` 得到的 `user.tenant_id/user.sub` 取 owner，body 不接收 owner 或候选 ID。`lifespan` 已把 `RedisSessionCache(PostgresSessionStore(...))` 放入 `app.state.session_store`，所以创建/授权方法应能沿这层代理到 PostgreSQL。`ChatRequest.session_id` 继续必填，并拒绝空白 ID（422）；两个聊天路由都先确认 store 可验证归属，否则 503；随后以当前 JWT 查 `authorize_session`，查不到统一映射为 404；通过后才限流、扣额度和进入业务函数。只把明确的“无权限/不存在”领域异常转 404，数据库连接故障不得伪装成 404。流式路由的归属检查必须在 `return StreamingResponse(...)` **之前**，不能放入异步生成器里，否则 HTTP 200 可能已经发送。

同时改 [async_agent.py](../app/async_agent.py)：`answer_question_async/stream_answer_question_async` 新增 `tenant_id, owner_sub` 参数，继续传到 `_load_history/_save_turn`，再传给 store 的 `get_messages/append_turn`。路由的限流 key 至少包含可信 `tenant_id/sub` 和 ID。HTTP 路由不能在 store 缺失时掉进 `_load_history/_save_turn` 的 `session_store is None` 内存 fallback；那条路径目前仅按 ID 隔离。**验收**：B/C 调 `/chat`、`/chat/stream` 得到一致的 404，不触发 LLM、消息读取或写入；无效 JWT 为 401；本人 ID 才进入限流/额度/模型路径。

**建议统一的函数参数顺序**：store 与缓存都采用 `create_session(tenant_id, owner_sub)`、`authorize_session(session_id, tenant_id, owner_sub)`、`get_messages(session_id, tenant_id, owner_sub)`、`append_turn(session_id, tenant_id, owner_sub, question, answer)`；业务函数采用 `answer_question_async(..., tenant_id=..., owner_sub=...)` 和 `stream_answer_question_async(..., tenant_id=..., owner_sub=...)`，内部 `_load_history/_save_turn` 同名传递。主路由不要接受 body 自报的 `tenant_id/owner_sub`。可以在存储模块定义一个 `SessionNotFound` 领域异常，由两个路由统一捕获并映射为相同 404；数据库连接错误继续作为服务故障处理。这样你改一个函数时可用搜索核对全部调用点。

##### **第 5 步：前端改为等待服务端 ID（约 15 分钟）。** 

在 [App.tsx](../frontend/src/App.tsx) 把聊天模式的初始 `sessionId` 改成“未创建”（如 `string | null`）；`resetConversation`/切模式清掉 ID。`submitChatOrAgent` 已按 `definition.endpoint` 分支：**仅当 endpoint 为 `chat`**，且 ID 为空时，先用 [apiFetch](../frontend/src/lib/api.ts) 发 `POST /chat/sessions`，检查 `201` 和响应中的 ID，再 `setSessionId`，并用**刚拿到的局部变量**构造 `/chat/stream` body（不要指望 `setSessionId` 立即更新本次函数闭包）。第二轮复用已保存 ID。创建失败时展示错误并停止发送；切模式、登出、从游客切到用户后清掉旧 ID，避免带原身份的 ID 续聊；Agent/JD endpoint 不调用建会话接口。已有 `sending` 状态需防止同一次用户操作重复建会话，快速连点时可用同步 ref/进行中的 Promise 兜住。**验收**：Network 中先出现 `201 /chat/sessions`，再出现携带同 ID 的 `/chat/stream`；第二轮不新建；身份或聊天模式变化后重新建；创建失败时没有聊天请求。运行 `npm --prefix frontend run test`、`npm --prefix frontend run build`。

##### **第 6 步：更新失败用例与回归（约 20 分钟起，实际按结果延长）。** 

目的不是让旧测试“绿掉”，而是证明**谁有权用哪个 ID，以及拒绝发生在读历史和调用模型之前**；存储事务、缓存和前端各有独立风险，须分别留断言。

##### 面试可复述答案：会话归属修复完整口述版

> 我的个人 AI Job Agent 使用 FastAPI、React、PostgreSQL 和 Redis。复习项目时，我沿着聊天路由、历史读取和保存源码，发现原实现虽然验证了 JWT，但消息和缓存主要按前端传入的 session_id 读写。JWT 只能证明请求者是谁，不能证明他有权访问这条会话；另一个持合法 JWT 的用户拿到 ID，就可能读取或写入别人的历史。我先用 fake 模型和会话 store 做 A/B 用例，把这个问题复现成可验证的行为。
>
> 修复时我采用独立的 POST /chat/sessions。服务端从已验证 JWT 取 tenant_id 和 sub，生成随机会话 ID，把它与 owner 一起写入新增的 chat_sessions 表，提交成功后才返回给前端。首条聊天先创建会话，后续复用 ID；切换聊天模式或身份时重置。服务端生成 ID 是创建契约的一部分，真正的安全保障仍然是归属检查。
>
> /chat 和 /chat/stream 都在进入模型与消息读取之前检查 session_id、tenant_id、owner_sub 的关联。流式接口尤其要在返回 StreamingResponse 前检查，这样越权请求直接收到 404，不能先返回 200 再在流里报错。不存在和无权限使用同样的 404，减少对象存在性泄露；无可用 store 则返回 503，不回退到只按 ID 分组的内存数据。
>
> 存储层也做约束。读取通过消息表关联会话表，并同时限制 ID、租户和 owner。写入在短事务里再次检查并锁定归属行，然后插入一条 user 和一条 assistant 消息，成功后提交，异常则回滚；我不会在等待模型生成时一直占着数据库事务。旧消息如果没有可信 owner，就保留但拒绝访问，不允许谁先请求谁认领。
>
> Redis 使用包含三元组的 key，并编码每个字段。命中缓存前仍查 PostgreSQL 归属；未命中才读取消息并缓存。保存时先提交 PostgreSQL，再删除缓存。实际存储实验中，一轮是两条消息，两轮是四条；第二次读没有增加 PG 消息查询，但仍增加归属检查，证明命中没有绕过授权。写入后 key 从存在变成不存在，这是主动失效，下一次读会回源最新消息。

##### 面试追问：把依据与取舍说清楚

**为什么不能只把 Redis key 加上用户？** 缓存未命中会回源。如果 PostgreSQL 仍只按 session_id 查询，就可能把 A 的消息读出来再写到 B 的新 key。key 负责分区与加速，归属表和读写授权负责权限，两层都要正确。

**为什么路由已经授权，写入还要查一次？** 路由检查保护进入模型前的入口；写入检查保护直接调用 store 的路径，也防止检查后、保存前归属发生变化。FOR UPDATE 在保存这段短事务中锁住归属行，不代表整个模型生成过程或同会话的并发聊天已经被串行化。

**缓存命中后还查 PG，会不会削弱缓存价值？** 是取舍。当前缓存减少的是完整历史消息读取，而不是完全消除数据库访问；每次先做小的归属查询，边界清楚，也便于处理将来的会话删除/权限变化。以后可设计授权缓存，但要解决过期、撤销与一致性，不能直接省掉检查。

**你怎么知道第二次是真的命中？AsyncMock 不是假结果吗？** 实验使用 AsyncMock(wraps=真实方法) 做调用计数，底层方法仍查真实 PG。第一次 get_messages 次数为 1；第二次仍为 1，而 authorize_session 次数增加到 2；再结合真实 Redis 中的 JSON 和 TTL，能够说明消息来自缓存且仍经过授权。普通 fake 测试与这种真实方法观察要区分。

**两个 skip 与真实实验通过矛盾吗？** 不矛盾。pytest 的两个集成用例看 TEST_DATABASE_URL/TEST_REDIS_URL；手工实验在容器中用应用配置的 DATABASE_URL/REDIS_URL 连接。它们是不同的运行入口，所以我要分别报告“哪些自动化执行了”和“哪些真实手测做过”。

```python
import uuid


class SessionNotFound(Exception):
    """当前身份无权使用此会话，或会话不存在。"""


class PostgresSessionStore:
    def __init__(self, pool):
        self._pool = pool

    async def create_session(self, tenant_id: str, owner_sub: str) -> str:
        session_id = uuid.uuid4().hex
        async with self._pool.connection() as conn, conn.cursor() as cur:
            try:
                await cur.execute(
                    """
                    INSERT INTO chat_sessions (session_id, tenant_id, owner_sub)
                    VALUES (%s, %s, %s)
                    """,
                    (session_id, tenant_id, owner_sub),
                )
                await conn.commit()
            except Exception:
                await conn.rollback()
                raise
        return session_id

    async def authorize_session(
        self, session_id: str, tenant_id: str, owner_sub: str
    ) -> None:
        async with self._pool.connection() as conn, conn.cursor() as cur:
            await cur.execute(
                """
                SELECT 1 FROM chat_sessions
                WHERE session_id = %s AND tenant_id = %s AND owner_sub = %s
                """,
                (session_id, tenant_id, owner_sub),
            )
            row = await cur.fetchone()
        if row is None:
            raise SessionNotFound()

    async def get_messages(
        self, session_id: str, tenant_id: str, owner_sub: str
    ) -> list[dict]:
        async with self._pool.connection() as conn, conn.cursor() as cur:
            await cur.execute(
                """
                SELECT m.role, m.content
                FROM chat_messages AS m
                JOIN chat_sessions AS s ON s.session_id = m.session_id
                WHERE m.session_id = %s
                  AND s.tenant_id = %s
                  AND s.owner_sub = %s
                ORDER BY m.id ASC
                """,
                (session_id, tenant_id, owner_sub),
            )
            rows = await cur.fetchall()
        return [{"role": role, "content": content} for role, content in rows]

    async def append_turn(
        self,
        session_id: str,
        tenant_id: str,
        owner_sub: str,
        question: str,
        answer: str,
    ) -> None:
        async with self._pool.connection() as conn, conn.cursor() as cur:
            try:
                await cur.execute(
                    """
                    SELECT 1 FROM chat_sessions
                    WHERE session_id = %s AND tenant_id = %s AND owner_sub = %s
                    FOR UPDATE
                    """,
                    (session_id, tenant_id, owner_sub),
                )
                if await cur.fetchone() is None:
                    raise SessionNotFound()
                await cur.execute(
                    """
                    INSERT INTO chat_messages (session_id, role, content)
                    VALUES (%s, 'user', %s)
                    """,
                    (session_id, question),
                )
                await cur.execute(
                    """
                    INSERT INTO chat_messages (session_id, role, content)
                    VALUES (%s, 'assistant', %s)
                    """,
                    (session_id, answer),
                )
                await conn.commit()
            except Exception:
                await conn.rollback()
                raise
```

from urllib.parse import quote

from app.redis_cache import RedisCache


class RedisSessionCache:
    def __init__(self, redis, postgres_store, ttl: int = 300):
        self._cache = RedisCache(redis)
        self._postgres_store = postgres_store
        self._ttl = ttl

    def _key(self, session_id: str, tenant_id: str, owner_sub: str) -> str:
        # guest 的 sub 含冒号；逐字段编码，避免不同三元组拼出同一个 key。
        return (
            f"chat:session:{quote(tenant_id, safe='')}:"
            f"{quote(owner_sub, safe='')}:{quote(session_id, safe='')}:messages"
        )

    async def create_session(self, tenant_id: str, owner_sub: str) -> str:
        return await self._postgres_store.create_session(tenant_id, owner_sub)

    async def authorize_session(
        self, session_id: str, tenant_id: str, owner_sub: str
    ) -> None:
        await self._postgres_store.authorize_session(
            session_id, tenant_id, owner_sub
        )

    async def get_messages(
        self, session_id: str, tenant_id: str, owner_sub: str
    ) -> list[dict]:
        await self.authorize_session(session_id, tenant_id, owner_sub)
        key = self._key(session_id, tenant_id, owner_sub)
        cached = await self._cache.get_json(key)
        if cached is not None:
            return cached
        messages = await self._postgres_store.get_messages(
            session_id, tenant_id, owner_sub
        )
        await self._cache.set_json(key, messages, self._ttl)
        return messages

    async def append_turn(
        self,
        session_id: str,
        tenant_id: str,
        owner_sub: str,
        question: str,
        answer: str,
    ) -> None:
        await self._postgres_store.append_turn(
            session_id, tenant_id, owner_sub, question, answer
        )
        await self._cache.delete(self._key(session_id, tenant_id, owner_sub))

**复杂度从“数工作量”开始。** 令 `T` 为实际模型调用轮数（`T ≤ max_steps`），`K` 为所有轮普通工具调用总数，`B` 为工具参数和 observation 总字符量。先暂时把 `model()` 和 handler 当作黑盒，只算这个 Python 循环：外层检查做 `T` 次，内层工具处理做 `K` 次，构造和保存内容涉及 `B` 个字符，因而本地控制逻辑约 **O(T + K + B) 时间**、保存完整消息约 **O(K + B) 空间**。如果只数对象个数且忽略字符串长度，可简写为 O(T+K) 时间、O(K) 消息空间。不能只写 O(max_steps)：一个模型响应可有多个 `tool_calls`，而 `max_steps` 只限制外层轮数。

**把模型与 fake 记录也算进去。** 每轮 `model(messages)` 会读取截至当时积累的消息；真实 API 的传输、计费和推理开销依赖每轮历史长度，不能当成固定 O(1)。骨架的 `_fake_model` 还会把每轮 `messages` 浅拷贝并保存在 `seen_messages`；因此完整自检的额外时间/空间与“每轮历史消息数之和”有关。若每轮大致增加固定 `k` 条工具消息，累计历史读取/拷贝量可到 O(k·T²)。这是**测试 fake 和真实上下文累积**带来的额外成本，不应冒充你的本地循环自身的固定复杂度。

**边界补充。** 当前代码在模型没有工具也没有有效 `content` 时会返回空答案；如果同一响应里先出现普通工具、后出现 `finish`，会提前返回，导致已执行工具的结果未进入 `messages`。这两类输入不在现有 4 个自检里。若要增强，先规定 `finish` 必须是本轮唯一调用，并在执行任何 handler 前验证整个调用列表；无有效答案时抛错。工具可能有副作用，不能先执行前一个再发现后一个非法。你可把这点作为口述边界，D3 不要求扩展练习代码。
