## 这套资料解决什么问题

你之前按 `docs/day1.md` 到 `docs/day70.md` 线性阅读，会出现两个问题：

1. 后面改动会覆盖前面的实现，例如 Day 11 的内存会话后来被 PostgreSQL + Redis 替换，Day 5 的简单向量检索后来变成混合检索加重排。
2. 按天数阅读得到的是“事件流”，不是面试真正需要的“结构流”。面试官问的不是“Day 23 你干了什么”，而是“你的 RAG 完整链路是什么，为什么这样设计，怎么验证”。

所以这套资料不按 1 到 70 天排列，而按 8 条业务与技术闭环组织：

## 建议复习顺序

不要一开始就背源码。先按下面顺序建立“可以讲出来”的结构：

```text
第一步：01 项目全景
  记住一句话定位 + 总架构图 + 四个核心闭环

第二步：03 Agent 核心链路
  这是整个项目的主线，先能闭眼讲 ReAct 循环

第三步：02 RAG 链路
  理解 Agent 调用最多的工具底层是什么

第四步：04 多 Agent 与 LangGraph
  理解从单 Agent 演进到有状态多 Agent 的原因

第五步：05 MCP + 06 安全
  它们是工具系统的标准接入与边界控制

第六步：07 后端生产链路
  把 Demo 变成一个可以多用户运行的服务

第七步：08 可观测性与部署链路
  解决“线上出错怎么查”和“怎么上线”

第八步：09 面试口述与追问清单
  做输出训练，而不是继续输入
```

## 记忆原则

### 1. 用“闭环”而不是“文件”记忆

每个链路都画成图，先记闭环里的节点和箭头，再记每个节点落在哪个文件。

例如 RAG 只记 7 个动作：

```text
切分 -> Embedding -> 入向量库 -> 查询 -> 混合检索 -> 重排 -> 注入生成
```

每个动作都对应一个词，比记“`chunking.py` 有 187 行”更稳定。

### 2. 每张图配一个“口述锚点”

看到图先做 30 秒口头复述，再打开源码。例如：

```text
用户输入 -> 清洗 -> 查历史 -> 可能检索知识库 -> 拼 Prompt -> LLM -> 保存会话 -> 返回
```

先能讲粗粒度，再补“为什么”：为什么先查历史，为什么要做上下文预算，为什么保存完整答案而不是流式片段。

### 3. 使用“问题 -> 方案 -> 取舍 -> 验证”四步卡

对每个重要模块，只记四句话，不要记函数签名：

```text
问题：长会话会把模型上下文撑爆。
方案：ContextBudget 用 tiktoken 估算 token，按消息组裁剪旧历史。
取舍：优先保留 system 和最近消息，牺牲最早上下文。
验证：单元测试覆盖裁剪、空输入、只保留 system 仍超限。
```

这套结构同时就是面试答案结构。

### 4. 分层记忆，别把 70 天当 70 个知识点

真正需要长期记住的是三层：

```text
概念层：RAG、ReAct、Function Calling、MCP、checkpoint、熔断
链路层：请求从 API 到模型再返回的路径
实现层：某个文件里的关键边界条件
```

先保证概念层和链路层，实现层只在被追问时定位到文件。

## 如何记得更清楚

### 主动回忆，而不是重复阅读

合上文档，在纸上写：

1. 总架构图。
2. ReAct 循环的 5 个关键点。
3. RAG 的 7 步。
4. 三条安全防线。

写不出来的地方，才是真正需要回看的节点。

### 用 Feynman 讲解法

假装给一个后端同学讲解 10 分钟。讲解时必须覆盖：

- 它是什么。
- 它解决什么问题。
- 它怎么工作。
- 如果不这样做会怎样。
- 怎么证明它有效。

卡住的地方，回到对应链路文件读源码。

### 建立“异常案例”记忆

面试官喜欢从失败场景追问。每个链路至少准备两个异常：

```text
RAG：查询改写失败怎么办，向量维度和模型不一致怎么办。
Agent：模型返回非 tool_calls 怎么办，危险工具不审批怎么办。
生产：Redis 宕机怎么办，数据库连接池耗尽怎么办。
```

本项目的源码多数都做了降级或显式报错，这些就是最好讲的细节。

## 面试表达建议

### 1. 项目自述控制在 5 到 8 分钟

建议顺序：

```text
项目定位 -> 技术栈 -> 架构分层 -> 核心链路 -> 一个最有价值的设计决策 -> 验证与边界
```

不要把 70 天都讲一遍。先讲“AI 求职分析 Agent 解决什么问题”，再讲“ReAct + RAG + 多 Agent + 生产化”，最后主动说一个取舍。

### 2. 回答采用“结论先行”

```text
结论：混合检索是为了补足向量检索对精确词法匹配的短板。
展开：向量擅长语义，BM25 擅长关键词。
取舍：两者分数范围不同，所以先归一化再加权。
验证：用 Recall@K、Precision@K、MRR 评测。
```

### 3. 面对追问先分类

| 问题类型 | 应对结构 |
|---|---|
| 概念题 | 一句话定义 + 类比 + 项目例子 |
| 流程题 | 画链路，按节点讲 |
| 对比题 | 表格对比 + 什么时候选哪个 |
| 故障题 | 现象 -> 定位 -> 根因 -> 修复 -> 验证 |
| 设计题 | 需求 -> 约束 -> 方案 -> 取舍 -> 风险 |

### 4. 展示“工程判断”

不要说“所有地方都用最新技术”。要能说出：

- 为什么低内存部署用远程 Embedding。
- 为什么 `apply_job` 只模拟，不接真实外部系统。
- 为什么 ObservabilityStore 当前是内存态，生产可替换。
- 为什么 LangGraph 超时用线程池实现，在高并发下需要换成队列或复用线程池。

这些“我知道边界”的表述，比假装完美更接近 30k 到 40k 岗位的判断力。
